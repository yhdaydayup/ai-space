# 维护（写入 / 查询 / 巡检 / 脱敏）

知识仓：`~/.ai-space/`。写入必须先拿到写锁，写完立刻释放。不要因为脏工作区就停——脏仓由拿到锁的写入者恢复并提交。不 force push。

没有 remote：不要 pull。有 remote：`git pull --ff-only`，快进失败则释放锁并停。

仓内 `sources/`、`wiki/`、`wiki-ext/`：按本文件写入并自行 commit，不必等人确认。仍要确认的只有外发：把 `wiki-ext/` 拷给外部 Agent，或把整仓 push 到别人能 clone 的网。

产品 skill 的发现与加载由各 Agent 环境自己做。L1 不读 `LOADOUT.md`，不按 always-on / recommend / catalog 调度。

## 分类

先看是不是原料：会议记录、PRD、导出 → `sources/`。代码仓、本机已有大目录 → 软链接 + index，禁止 `cp -R` / clone 进 `sources/`。线上文档只记 URL。

其余问：下次是再执行一遍这套动作，还是查询已定事实？

- 再执行一遍 → 各环境里的产品 skill，不写进本仓当门禁账本
- 查询事实 / 实体 / 结论 → `wiki/`

`wiki-ext/` 不是第三种知识。它是 `wiki/` 的对外副本。本机查知识仍读 `wiki/`。

密钥、私钥、`.env` 原文三层目录都不放。

## 写入互斥（本机多 CLI / 多会话）

同一时刻只允许一个写入者。锁在 `~/.ai-space/.git/ai-space-write.lock/`（不进 git）。Agent 每次命令都是短进程，所以锁靠时间戳（默认 30 分钟过期），不靠 PID 是否还活着。

脚本：本包 `scripts/write-lock.sh`。一次写入只 `prepare` 一次，不要在同一轮里再跑 `prepare`（会等自己的锁直到超时）。

1. 开始写：`scripts/write-lock.sh prepare`
   - 拿到锁；最多等 90 秒
   - 无 remote 跳过 pull；有 remote 则 `--ff-only`
   - 工作区有未提交改动且无冲突：先 commit「Recover interrupted knowledge-store write.」再继续你的写入
   - 有未合并冲突：释放锁，停，告诉用户
2. 写入可能超过 25 分钟：中途 `scripts/write-lock.sh heartbeat`
3. 你的内容 commit 完：`scripts/write-lock.sh release`
4. 中途放弃：也要 `release`，不要留锁

`prepare` 因 busy 失败：告诉用户「仓正在被另一个会话写入，请稍后让我再试」。这不是永久停写。不要另建一份仓。锁过期后下一个 `prepare` 会抢走并恢复脏仓。

禁止：跳过脚本直接改 wiki；把脏仓理解成「全员停写」。

## 查询

不要对 `~/.ai-space/` 做全目录搜索当默认路径。每个 index 每行 = 链接 + 一句能区分相邻页的说明。

- 本机知识：`wiki/index.md` → 只打开点到的页 → 对不上再读 `sources/`（软链接只打开被点到的文件，不读整棵目标树）
- 外部知识：只走 `wiki-ext/index.md`。对不上就停，不准读 `wiki/` 或 `sources/`

## 何时写入

没有关键词、斜杠命令或固定话术。开机不写。自然语言说「整理 / 写入 / 巡检」可以触发，但不是门槛。

**拍板即写入。** 下面任一成立，当时就走「整理进原生 wiki」，不必等人再下指令：

- 用户确认了一个可复述的结论（走 A、就这样、对齐了、可以落地、以这个为准）
- 用户纠正了 Agent 的理解，且纠正本身是长期事实（职责、门禁、字段、所有权）
- 多选已经收成单一结论，下次会来查「这事怎么定的」

只写结论和必要指针，不把讨论过程抄进 wiki。先读 `wiki/index.md`，能并进已有页就并。这一步不生成 wiki-ext。

不写：编译、安装、rebase、删注释、纯排障且没有可复用结论；仍在枚举选项、未收口；一次性数值或当场就会过期的状态。

原料（妙记、PRD 导出、大源指针）在第一次拿到时放入 `sources/`，不必等拍板。巡检时机见下文，不是开机必跑。

## 写入

下面各小节默认已经 `prepare` 成功。整次维护（原文 / wiki / 巡检 / 生成 wiki-ext）共用这一次锁，最后 `release`。

### 放入原文

1. 大源（代码仓、数据集、模型、大体积导出）：`ln -s` 指向本机已有路径。git 只提交链接本身。在 `sources/index.md` 写：本机路径、git URL（若有，必要时 branch/commit）、一句话。禁止整份拷进仓。
2. 飞书 / 内网文档：index 只记 URL 和一句话，不下载整份。
3. 妙记、一页 PRD、摘录：文件放进 `sources/`，只增不改，更新 index。
4. 密钥、私钥、`.env` 不准进；也不要把它们所在目录整棵链进来。
5. 确认 git 新增的是软链接而不是目标文件，然后 commit。

软链接断了：按 index 里的路径 / git URL 重建，不要拷一份进来顶上。

### 整理进原生 wiki

1. 能并进已有页就并，否则新建。更新 `wiki/index.md`。新页链到相关旧页，旧页也链回来。
2. 这一步可以留真名、司内细节、1on1。不要在这里做脱敏。
3. 可复用原则单独写到主题页并链回当次决策页；当次取值留在较具体的那一页。
4. 自行 commit。禁止把 `wiki/` 直接拷给外部。
5. 整次维护结束再 `release`。

## 脱敏规则

从 `wiki/` 投影到 `wiki-ext/`。原生页不动。sources 永不进 wiki-ext。没生成、清单没列全、人没确认 → 不把 wiki-ext 交给外部。

按段落分类。说不清按禁止。

| 类别 | 进 wiki-ext？ |
| --- | --- |
| 密钥（能用来登录、调接口、解密） | 禁止。原生也不该有；发现了两边都删，停外发直到清掉 |
| 司内密文 | 允许 |
| 工作身份（履职需要的人名与职责） | 允许，保留真名 |
| 敏感个人（1on1 原文、绩效薪酬晋升、家庭住址电话、健康、私人 git/账号） | 禁止 |
| 通用（拿掉上面两类后仍成立） | 允许 |

四种改法，按序选一种，报告里写明用了哪一种：

1. **删除** — 对外页不需要，或信息本身不能给同事
2. **改写留结论** — 丢掉私密过程，留下决定或事实。例：1on1 改成「PM 张三要求加宽表字段」
3. **泛化** — 换成角色、类别或量级，且不能反推原文
4. **整页不生成** — 拿掉禁止内容后这页不再成立

四种都做不到 → 该页移出清单，或整次取消。密钥不准打码留半截、不准编假 token。人事与生活整段删除，不泛化数字。履职姓名不要无故改成「某 PM」。本机路径 `/Users/姓名/...` 删掉用户名，改成「本机仓库」或删除。说不清能否给同事的链接删 URL。

wiki-ext 页只链其他已生成的 wiki-ext 页，不要链 `sources/` 或 `wiki/`。未生成的原生页：去掉该链，或改成不带链接的「见内部页（未对外）」。同一人在多页称谓要一致。

验收：对照原生页逐段看 wiki-ext；禁止内容为零；工作结论没有被改歪；每处改动能在报告里找到「原文摘录 → 类别 → 改法」。

## 巡检

不是开机必跑。写入后结构坏了、刚收进一批材料、刚更新过 wiki / wiki-ext、或要检查知识仓时做。三条轴都要过。可以按本次改动收窄正文范围，但三份 index 要整份看。

巡检过关 ≠ 可以外发。

1. **定范围。** 整仓，或「某次写入涉及的页 + 它们所在的 index」。范围内已有 wiki-ext 页，脱敏轴必查对应原生页。
2. **索引效率。** 只打开三份 index。对每个条目问：只靠这一行，能不能决定要不要打开。记下含糊、撞车、无分组、大源只指到仓库根、wiki-ext 目录带敏感词或比原生更难用。
3. **正确性。** index 与文件一一对应；链接打得开；入库副本没被改过；没有大源整份拷贝；软链接能解析，不能解析时 index 有可重建定位；wiki 没改 sources 原文；同一事实两页打架须标明以谁为准；wiki-ext 不链到原生层。
4. **脱敏。** 对范围内每个 wiki-ext 页：机械扫描（同生成流程）→ 通读按禁止表打档 → 对照原生页看是否投影、结论有没有被改歪、改法有没有用错。原生 wiki 同样扫密钥，命中则两边都删。已对外交付过、或 index 仍列着、却未扫过的页，记为覆盖缺口。
5. **按协议修。** 效率优先改目录说明和分组，不要把正文堆进 index。正确性按写入规则改。脱敏按四种改法改 wiki-ext（密钥同时改原生），不要手写一套对不上的对外稿。
6. **再读** 三份 index，抽查刚修过的 wiki-ext 页。
7. **自行 commit。** 记录范围、效率问题、正确性问题、脱敏命中（原文摘录 → 类别 → 改法）、改了哪些文件。整次维护结束再 `release`。

过关：正确性、脱敏表没有未处理项；抽一个以后会问的问题，只靠 index 能选到唯一合理的下一篇（或明确「仓里没有」）。

### 正确性不合格

- sources：文件或软链接不在 index；index 指向不存在的路径；改了已有入库副本；进了密钥 / `.env`；大源整份拷贝；软链接损坏且 index 没有可重建定位
- wiki：有页不在 index；死链；新 source 没挂到相关 wiki；wiki 改了入库原文；同一事实两页矛盾且未标明以谁为准
- wiki-ext：有页不在 index；死链；链到 `sources/` 或 `wiki/`（禁止内容归脱敏轴）

### 索引效率不合格

- 目录里有页却不在 index；index 有条目但目标不存在；一行没有说明，或两行说明几乎一样
- wiki/index 一长串没有分组；一页塞多个互不相关主题；能并进已有主题页却新建了孤岛页
- sources/index 软链接只写仓库根，没写 wiki 实际用到的子路径；小材料重复入库多份
- wiki-ext/index 列出未生成的原生页；说明里带敏感个人或密钥；条目比原生 index 更含糊

## 生成脱敏 wiki

一次只处理一份列清楚的页面清单。不要说「把整个仓脱敏一下」却不给路径。清单来自点名的路径，或相对上次已提交 wiki-ext 的 diff。除非明确要全量，否则不要默认整个 `wiki/`。点的是目录必须展开成文件列表。清单出现 `sources/` → 整次失败。

1. 说明本次是更新 wiki-ext 给外部 Agent。没说清就停，问一句。
2. 列出将生成的每一个原生页路径，排除 sources。
3. 对每个文件做机械扫描，命中必须写进报告。至少查：password / token / secret / Bearer / BEGIN PRIVATE / AKSK 形态；`/Users/`、`~/.ssh`、`.env`；1on1、绩效、薪酬、晋升、家人、住址、私人手机号。内网域名见附录。误报写「误报 + 理由」。
4. 通读每段，按分类表打档。扫描没扫到但属于敏感个人或密钥的，同样记下。
5. 只改 wiki-ext。对每一处禁止内容选一种改法。做不到、而人又要求必须给出去 → 整次取消。原生页保持原样。
6. 更新 `wiki-ext/index.md`，只保留实际写出的页。对外页链接只指向其他 wiki-ext 页。未处理项为空即可 commit 进知识仓。
7. 写报告：清单；每条命中的原文摘录、类别、改法、改成了什么。
8. 只有要把 wiki-ext 拷给外部时，才等人确认「可以外发」。未确认不准拷贝。仓内生成和提交不必等这一步。

可以交给外部的条件：未处理项为空，人已确认，对方实际拿到的文件都在 wiki-ext 里。跳步骤、夹带原生页、改原生、「大部分过了就先给」、只做正确性巡检没跑脱敏轴就当可以外发，都不算过关。

禁止：未确认就开始拷贝；把 `~/.ai-space/` 整仓交给外部；报告没有摘录；密钥打码后仍把能复原的半截写进 wiki-ext。

## 附录：机械扫描

内网域名至少：`*.bytedance.net`、`code.byted.org`。

同一段怎么改（示例）：

原生：「需求 N123：和 PM 张三 1on1 里他说加宽表字段；设计在飞书文档；token=abc；我私下觉得这会影响陪家人的时间；原则是宽表不如事件表。」

对外：「需求 N123：PM 张三要求加宽表字段；设计在飞书文档；原则是宽表不如事件表。」

- 需求号、飞书链 → 司内密文，保留
- PM 张三 → 工作身份，保留
- 1on1 原文 → 改写留结论
- token=abc → 密钥，两边都删
- 陪家人 → 敏感个人，删除
- 宽表不如事件表 → 通用，原样

个人 AI 知识仓

给本机 Cursor / Claude 用的一份知识 git，以及告诉 Agent 怎么用这份仓的薄协议。外部 Agent（Aime / Mira 等）只能看到脱敏后的 wiki。

1. 解决什么问题、提供什么能力

问题：每次问 Agent，都从会议记录、PRD、聊天记录里临时翻答案。

这样做贵、不稳定，下次还要重来；也容易把不该给同事看的原文带出这台机器。

这份仓提供三件事：

  1. 把原料收起来。小材料（妙记、PRD 导出、摘录）进 sources/ 当副本；代码仓、大数据源只记指针（软链接 + 定位信息），不把整份拷进来。
  2. 把长期知识写下来。字段含义、已拍板结论、可复用原则写进 wiki/。下次问「这事怎么定的」，先读 wiki，而不是整份妙记。
  3. 把对外可见的知识和本机全量知识分开。本机用带真名和司内细节的原生 wiki；给外部 Agent 的是另一棵 wiki-ext/，敏感个人和密钥不在里面。

Cursor 和 Claude 读写同一份仓。知识仓里的数据由 Agent 按协议自行维护和提交，不必等人确认；人也可以直接改文件。自然语言只是一种触发方式，不是规定动作。把内容交给外部 Agent 时仍要等人确认。

2. 用什么方式实现

两样东西，不混在一个 git 里：

  • 知识仓：工作副本固定在 ~/.ai-space/，一个 git。里面是 sources 和两层 wiki。
  • L1：一个独立的 skill 包，装在 Cursor / Claude 各自的 skill 目录里。开机只读它的薄 SKILL.md，里面写清仓在哪、目录必须长什么样、怎么查、怎么更新。完整步骤放 references/maintain.md，用到再读。产品 skill 怎么加载，L1 不管。

知识不是每次从原文检索拼出来的，而是先写入 wiki，再按目录打开。对外也不是把本机 wiki 改成「已脱敏」——那样自己以后查不到真名——而是按规则从原生 wiki 生成一份副本 到 wiki-ext/。

本机 Agent 看得到整仓。外部 Agent 只拿到 wiki-ext/ 的拷贝，看不到 sources/ 和原生 wiki/。知识仓可以 push 到只有自己能读的 remote；同事能 clone 的网只接收导出的 wiki-ext/。

3. 整体架构

L1 协议包

不是知识正文。告诉任意已安装它的 Agent：仓的路径、目录约定、如何查 wiki、如何写入、如何生成对外副本。不管产品 skill 加载。

知识仓 git

~/.ai-space/。一份真本，本机多个 Agent 一起读写。L1 不进这个 git。

知识仓内部
本机可见

sources/ 原文；wiki/ 全量已整理知识（可留真名、司内细节、1on1）。

外部可见

只有 wiki-ext/。从 wiki/ 按禁止表生成。密钥和敏感个人不在这里。

谁读什么：

本机 Cursor / Claude外部 Agent（Aime / Mira / 共享会话）
L1开机读 SKILL.md不需要整仓协议；只使用交付的 wiki-ext
sources / wiki按第 4 节规则按需读没有这些目录

4. 使用说明 · 协议

下面这些规则始终成立。Agent 写入或查询时按这些做，不按「这次方便」放宽。

仓必须长什么样

必须有 - sources/index.md - wiki/index.md - wiki-ext/index.md 可以有 - sources/ 下的原文，或指向本机已有数据的软链接 - wiki/ 下的页面 - wiki-ext/ 下与原生对应的对外页 禁止 - 改 sources 里已经存在的原文（软链接指向的外部仓除外，那是别人的工作树） - 把代码仓库、数据集、模型、大体积导出整份拷进 sources/ - 把整个仓灌进一次对话的上下文 - 顺着 sources 里的软链接把目标整树灌进上下文 - 外部 Agent 读 sources/ 或 wiki/ - 为了对外把 wiki/ 里的真名改掉 - 人未确认就把 wiki-ext 交给外部，或把整仓 push 到别人能 clone 的网 - 密钥、私钥、.env 原文进这个仓（三层目录都不放）

契约写在 L1 的 SKILL.md 里，不另建 SCHEMA.md。也不用 AGENTS.md 当仓规则文件名，避免被 Cursor / Claude 当成工作区规则自动整份灌入。

L1 不管：你个人的行文风格、各环境有哪些产品 skill、当前需求做到哪一步。

新内容写到哪

仓里两类正文职责不同，不要混着用。

放什么Agent 什么时候读例子
sources/ 原料。小文件只增不改。代码仓和大体积数据源用软链接指向原位置，知识仓里不保存整份。 默认不读。本机查 wiki 对不上时，再按 sources/index.md 去翻；软链接只打开点到的文件，不读整棵目标树。 评审妙记、PRD 导出；软链接到本机代码仓
wiki/ 根据 sources 整理后的长期知识：事实、实体、已拍板结论、可复用原则。 本机要查「这事怎么定的」：先读 wiki/index.md，再只打开点到的那一页。 授权周期字段怎么填；某需求决定用事件表

wiki-ext/ 不是第三种知识。它是 wiki/ 的对外副本。本机查知识仍读 wiki/。

先看是不是原料：会议记录、PRD、导出文件 → sources/，不要改写成 wiki 冒充原文。代码仓、本机已有的大目录 → 按下一节记指针，不要拷贝。

其余：要查询已定事实或结论 → wiki。要再执行一遍的操作 → 各 Agent / CLI 环境里的产品 skill，不要在本仓做加载门禁。

何时写入

没有关键词、斜杠命令或固定话术。开机不写。人说「整理 / 写入 / 巡检」可以触发，但不是门槛。

拍板即写入。会话里一个下次还会来查的结论已经收成「以这个为准」，当时就写入 wiki/ 并 commit，不必等人再下指令。只写结论，不写讨论过程。先对照 wiki/index.md，能并进已有页就并。这一步不生成 wiki-ext/。

写不写
用户确认了方案、门禁、字段、职责或所有权（走 A、就这样、对齐了、可以落地）。用户纠正了理解，且纠正本身是长期事实。多选已经收成单一结论。 编译、安装、rebase、日志、当场会过期的数值，以及还没分出对错的选项。排障里已经能复述的原因、所有权、字段、门禁、生命周期，照写。

原料（妙记、PRD 导出、大源指针）第一次拿到就放入 sources/，不必等拍板。还没进 sources/index.md 的会话树当轮补指针。已经软链的会话树会自己长，不要逐条再记。

大源只记指针，不入库整份

知识仓不是第二个代码托管，也不是网盘。真本已经在别处维护的东西，sources/ 里只留能找到它的指针，让本机 Agent 需要时顺着去读，而不是再存一份会过期的拷贝。

怎么处理例子
拷进 sources/ 的小材料体积小、没有更好的本机真本，或需要一份不会被上游改掉的快照。妙记导出、一页 PRD、聊天摘录
软链接 + index 定位本机已有、且会继续变的大目录。业务代码仓、数据集、日志包、模型文件
只写 URL，不下载真本在线上，本地没有、也不该镜像整站。飞书文档、内网 wiki；index 里记链接和一句话，不把网页另存进仓

做软链接时，知识仓 git 只提交这个链接本身（一段路径），不提交链接目标里的文件。同时在 sources/index.md 写清定位，换机器后能重建：

  • 本机路径（软链接指向这里，例如 ~/work/capcut）
  • 若是 git：remote URL，必要时加默认 branch / commit
  • 一句话：这是什么、wiki 为什么要指到它
# sources/index.md - [2026-08-19 需求评审妙记](meetings/2026-08-19-review.md) — 授权表字段讨论（入库副本） - [PRD 原文](prd/auth-period.docx) — 产品文档导出（入库副本） - [CapCut Android](repos/capcut) — 软链接 → ~/work/capcut；git: ssh://…/capcut.git

Agent 写入时：对代码仓和大目录执行 ln -s 指向已有路径，禁止 cp -R / clone 进 sources/。读的时候只打开 wiki 或 index 点到的那个文件，禁止把软链接目标整仓读进上下文。

软链接断了（换机器、目录搬家）：按 index 里的 git URL 和路径重建链接，不要改去拷一份进来顶上。绝对路径因机器而异，以 index 里的定位为准，不要假定别人 clone 知识仓后链接一定能用。

产品 skill 不归 L1

2026-09-10 起，L1 不再用 LOADOUT.md 或 always-on / recommend / catalog 控制产品 skill。多 CLI、多身份下，仓内账本适配不了当前 Agent 环境。

产品 skill 由 Cursor / Claude Code / 各 CLI 自己发现和加载。L1 只约定知识仓。不要在开机时读 skills/LOADOUT.md。

怎么查知识

不要对整个 ~/.ai-space/ 做全目录搜索当默认路径。

谁查什么怎么走
本机知识wiki/index.md → 只打开点到的页 → 对不上再读 sources/。默认不读 sources。若 source 是软链接，只读被点到的目标文件，不读整棵树。
外部知识只走 wiki-ext/index.md。对不上就停，不准去读原生 wiki 或 sources。

每个 index 每行 = 链接 + 一句话，用来判断要不要点进去。这句话必须能把该页和相邻页区分开，否则巡检里算索引效率不合格。

# wiki/index.md（本机） - [授权周期表](entities/auth-period.md) — 字段含义与写入规则 - [强插能力](topics/feed-insert.md) — story_recommend 承接 UG 素材的通用机制 # wiki-ext/index.md（外部） 结构相同，但只列出已经生成过、且通过对外禁止表的页。 原生有、这里没有的页，对外部当作不存在。 # sources/index.md - [2026-08-19 需求评审妙记](meetings/2026-08-19-review.md) — 授权表字段讨论（入库副本） - [CapCut Android](repos/capcut) — 软链接 → ~/work/capcut；git: ssh://…/capcut.git

什么可以给外部看

「生成对外副本」= 按下面的分类和改法，从 wiki/ 写出 wiki-ext/。原生页不动。

这不是少给几个 sources 文件——sources 本来就不给外部。也不是把本机 wiki 改干净。

默认不给

没生成、清单没列全、你没确认 → 不把 wiki-ext 交给外部，也不把它放到别人能 clone 的网。

不改原生

禁止为了对外把 wiki/ 里的真名改掉。改只发生在 wiki-ext/。

只给清单里扫过的页

没点名、没扫过的原生页不准出现在 wiki-ext。sources/ 永不进入。

按同事可见性把关

wiki-ext 的读者 = 能用该外部 Agent 的同事。敏感个人和密钥必须在生成时去掉，不能指望对方少读几个文件。

本机读 wiki、只整理原生 wiki、本地 commit：都不必生成对外副本。把 wiki-ext/ 写进知识仓属于数据维护，Agent 按协议生成并可以自行提交。拷给 Aime / Mira / 共享会话，或把 wiki-ext 放到别人能 clone 的 remote：必须等人确认之后再交出去。

按段落分类。一个原生页可以同时有几类内容；wiki-ext 只保留允许留下的信息。

这类内容怎么判断进 wiki-ext？
密钥这段能否直接用来登录、调接口、解密？禁止。原生 wiki 也不该有；发现了两边都删，停外发直到清掉。
司内密文离开公司或给未授权同事，是否泄密或违规？允许（读者是工作侧同事）。
工作身份是否只是履职需要的人名与职责？允许。
敏感个人是否与履职无关，或仅少数人应知的人事/私生活？禁止。包括 1on1 原文、绩效薪酬晋升、家庭住址电话、健康、私人 git 与账号。
通用拿掉司内密文和敏感个人后仍然成立？允许。

说不清算哪类、说不清飞书链能否给同事 → 按禁止处理。不准先给出去再补。

怎么做信息脱敏

分类之后，对每一处禁止内容必须选用下面四种改法之一，并在报告里写明用了哪一种。不准只标「已脱敏」却看不出改了什么。

改法做什么什么时候用
删除这句或这段不出现在 wiki-ext。对外页不需要这条信息，或信息本身不能给同事（密钥、薪酬、住址、健康）。
改写留结论丢掉私密过程，留下同事需要的决定或事实。真正有用的是结论，包着它的是 1on1 原文、私下判断、情绪。
泛化把具体值换成角色、类别或量级，且不能从结果反推出原文。需要有个指代（本机路径、数量级），但不需要真值。
整页不生成wiki-ext 里没有这一页，index 也不列。拿掉禁止内容后，这页不再成立，或只剩空壳。

挑选顺序：不需要这条信息 → 删除；需要结论不需要过程 → 改写留结论；需要指代不需要真值 → 泛化；整页离开禁止内容就不成立 → 整页不生成。四种都做不到 → 该页移出清单，或整次取消。不要硬编一版「看起来干净」的对外稿。

按类别怎么改

类别做法对外页可以写成不准写成
密钥 删除。原生 wiki 里若发现，也删，并停止外发直到清掉。 不出现。需要说明有凭证时写「凭证存在本机密钥管理，不入库」。 ak***xyz、保留后四位、编一个假 token、写在注释或代码块里。
敏感个人 · 1on1 / 私下判断 不抄对话和私人理由。若里面有工作决定，改写留结论。 「PM 张三要求加宽表字段。」 「1on1 里他说……」；「我私下觉得会影响陪家人的时间。」
敏感个人 · 人事与生活 删除整段。绩效、薪酬、晋升材料、家庭住址电话、健康、私人 git、私人账号，一律不改写、不泛化数字。 不出现。 「薪酬大约 xx 万」；「住在某小区」；私人仓库地址打码。
工作身份 履职需要的姓名和职责原样保留。wiki-ext 的读者是同事，不必改成「某 PM」。 「PM 张三」「接口 owner 李四」。 把履职姓名无故改成「某同事」。若这段其实在讲私人关系（「张三是我大学同学」），按敏感个人删除。
司内密文 需求号、未公开方案、能给同事用的内网/飞书链接，保留。 「需求 N123」；完整飞书文档链（确认能给同事）。 说不清能否给同事的链接还留着。本机路径 /Users/张三/... 要删掉用户名，改成「本机仓库」或删除。
通用 原样保留。不要顺手改技术结论的措辞。 「原则是宽表不如事件表。」 为了「更像对外文档」把结论改成另一套说法。

链接和结构

  • wiki-ext 页不要链到 sources/ 或 wiki/。只链其他已经生成的 wiki-ext 页。
  • 原生页指向的某页若这次没有生成对外副本：去掉该链，或改成不带链接的文字「见内部页（未对外）」。
  • 同一人在多页 wiki-ext 里称谓要一致：履职场景都用真名，不要一页真名一页「某 PM」。

改完怎么验收

对照原生页逐段看 wiki-ext：禁止内容为零；工作结论没有被改歪；每处改动能在报告里找到「原文摘录 → 类别 → 改法」。做不到这三项，不算脱敏完成。

巡检查什么

巡检有三条轴，都要过。只修死链、不看目录能不能用、不按脱敏规则核对 wiki-ext/，都不算做完。

轴问的问题不合格时会怎样
正确性仓里的事实和结构是否自洽，有没有违反写入、指针协议。查到假结论、改坏的原文、目录对不上、大源整份拷进来。
索引效率只读三份 index，能否选对下一篇，而不用扫整仓。每次都把半个仓打开；或有页永远找不到。
脱敏已生成的 wiki-ext/ 是否按「什么可以给外部看 / 怎么做信息脱敏」从原生 wiki 投影；原生层是否夹带密钥。外部若拿到这份 wiki-ext，会看到 1on1、密钥、敏感个人，或看到和原生对不上的另一套说法。

不是开机必跑。写入后结构明显坏了、刚收进一批材料、刚更新过 wiki / wiki-ext、或要检查知识仓时做。Agent 按协议直接改并提交，不必等人批准。

巡检里的脱敏检查，是把仓内 wiki-ext/ 修到符合协议。能不能把这份目录拷给外部 Agent，仍要单独确认，不因巡检绿灯而放行。

正确性

对象不合格
sources有文件或软链接不在 index；index 指向不存在的路径；改了已有入库副本；进了密钥 / .env；把代码仓或大数据源整份拷进来；软链接损坏且 index 没有可重建的 git URL / 路径
wiki有页不在 index；index 或正文里有打不开的链接；新 source 没有挂到相关 wiki；wiki 改了 sources 里的入库原文；同一事实两页互相矛盾且未标明以谁为准
wiki-ext有页不在 index；死链；链到 sources/ 或 wiki/。禁止内容、投影是否忠实，归下面「脱敏」轴，不在这里重复打勾就算过。

索引效率

查询协议规定：先读 index，再只打开点到的那一篇。巡检要验证这条路走得通、走得快。

对象不合格
所有 index有页/文件在目录里却不在 index（找不到）；index 有条目但目标不存在（空跑）；一行只有文件名没有说明，或两行说明几乎一样，无法判断该开哪篇
wiki/index.md条目一长串没有分组，读完 index 仍不知道去哪；一页塞了多个互不相关主题，index 无法指向「这一问该看哪一节」；能并进已有主题页的内容却新建了孤岛页
sources/index.md软链接只写了仓库根，没写 wiki 实际用到的子路径或文件，Agent 只能把整树当原文；小材料重复入库多份、index 无法区分哪份是当前锚点
wiki-ext/index.md列出了未生成的原生页；说明里带了敏感个人或密钥；条目比原生 index 更含糊，外部 Agent 更难选页

修索引效率时：改一句话说明、给 index 加分组小标题、合并孤岛页、拆厨房水槽页、给大源 index 补上具体子路径。不要靠「把更多正文写进 index」来解决——index 仍应是链接 + 一句能做决定的话。

脱敏

对照「什么可以给外部看」和「怎么做信息脱敏」逐项核对。范围：wiki-ext/ 里已有的页，以及对应的原生 wiki/ 页；原生层还要扫密钥（密钥两边都不准有）。

检查项不合格怎么修
密钥wiki/ 或 wiki-ext/ 里出现可登录、调接口、解密的原文；或打码后仍能复原的半截。两边都删。停外发直到清掉。不准用假 token 顶上。
wiki-ext 禁止内容1on1 原文、私下判断、绩效薪酬晋升、家庭住址电话、健康、私人 git / 账号仍留在对外页；index 说明里也带这些。按改法处理：删除，或改写留结论（「PM 张三要求加宽表字段」）。人事与生活整段删除，不泛化数字。
投影是否从原生出wiki-ext 有页、wiki 没有对应页；或对外页讲的是另一套故事，对不上原生结论。从原生重新投影。禁止为了过检手写一份「干净稿」。原生没有的页，从 wiki-ext 和它的 index 拿掉。
原生已改、对外未跟wiki 改过的页，wiki-ext 仍是旧正文，或仍含已过时的禁止内容。按当前原生页重做投影，报告里写原文摘录、类别、改法。
改法用错履职姓名被无故改成「某 PM」；飞书链说不清还留着；本机 /Users/姓名/... 还在；对外页链到 sources 或 wiki。工作身份保留真名；说不清的链接删 URL；路径改成「本机仓库」或删除；链接只指向其他 wiki-ext 页。
覆盖缺口某页已对外交付过，或 index 仍列着，但文件已不在 / 从未按禁止表扫过。补做投影，或从 wiki-ext/index 删除该条。没有 wiki-ext 的原生页可以只留本机，但 index 不准列它。

脱敏轴过关：wiki-ext 里禁止内容为零；每页能指回原生页且结论没有被改歪；每处修改能对应到一种改法。这仍不等于可以把目录拷给外部——拷贝前还要人确认。

仍要等人确认的，只有把 wiki-ext/ 拷给外部 Agent，或把整仓 push 到别人能 clone 的网。那是外发，不是仓内维护。

5. 使用说明 · 流程

维护知识仓不规定必须用自然语言。Agent 按协议改文件并提交；人也可以直接改。会话里用一句话触发也可以，但不是门槛。完整步骤写在 L1 的 references/maintain.md，做到那一步再读，不必开机就读。

新机器 / 新 Agent

  1. 按该产品的方式安装 L1。
  2. 把知识仓的 git 地址交给已经能读 L1 的 Agent。
  3. Agent 读 references/init.md，把仓 clone 到 ~/.ai-space/（这里必须是这个仓的工作副本）。
  4. 把 L1 装进当前产品的 skill 路径，并写上开机钩子：新对话开始时 Read L1 的 SKILL.md。
  5. 给外部 Agent 不要 clone ~/.ai-space/，只导出已确认的 wiki-ext/。

一次新对话开始时

本机

  1. 读 L1 的 SKILL.md。
  2. 知识仓根目录是 ~/.ai-space/。没有这个仓就停，先做上一节初始化。
  3. 不要把 wiki / sources 整仓灌进上下文。开机先不打开 maintain.md。
  4. 开机到此不是会话结束。可复述的结论当轮写入 wiki。新拿到的妙记、PRD、导出，或还没进 sources/index.md 的会话树，当轮放入 sources。已经软链的会话树不要逐条再记。不要等用户说「记下来」。

外部

  1. 只接收 wiki-ext 的一份拷贝（会话临时目录即可）。
  2. 查知识只走 wiki-ext/index.md。
  3. 路径里如果出现 sources/ 或 wiki/，当作不存在，不准去读。

往仓里写东西

拍板即写入，见 何时写入。不必等人说「整理 wiki」。

放入原文

  1. 先判断是小材料还是大源。代码仓、数据集、模型、大体积导出：在 sources/ 下建软链接指向本机已有路径，并在 sources/index.md 写下路径、git URL（若有）和一句话。禁止把整份拷进仓。
  2. 飞书 / 内网文档：只在 index 里记 URL 和一句话，不下载整份进仓。
  3. 妙记、一页 PRD、摘录：文件放进 sources/，只增不改，更新 index。
  4. 密钥、私钥、.env 原文不准进；也不要把它们所在的目录整棵链进来。
  5. 自己检查 git 里新增的是软链接（一段路径）而不是目标目录的文件，然后可以 commit。

整理进原生 wiki

把新材料写进 wiki/：能并进已有页就并，否则新建，改 wiki/index.md。新页链到相关旧页，旧页也链回来，避免多一个找不到的文件。

  1. 先 write-lock.sh prepare（无 remote 不 pull；脏仓恢复提交，不要停写）。
  2. 写入页面、补双向链接、更新 index。
  3. 这一步可以留真名、司内细节、1on1。不要在这里做脱敏。
  4. 可以自行 commit，然后 release。若这次要把知识交给外部，再走「生成脱敏 wiki」，禁止把 wiki/ 直接拷走。

需求里如果抽出了以后还能用的原则，单独写到主题页并链回当次决策页；当次取值和拍板过程留在较具体的那一页。不要只把原则埋在某一篇需求记录里。

巡检

一次巡检必须三条轴都跑：先索引效率（只读目录），再正确性（结构核对），再脱敏（对照原生页和禁止表核对 wiki-ext）。可以按本次改动收窄正文范围，但三份 index 要整份看。

  1. 定范围：整仓，或「某次写入涉及的页 + 它们所在的 index」。凡范围内已有 wiki-ext 页，脱敏轴必查对应原生页。
  2. 索引效率。只打开三份 index。对每个条目问：只靠这一行，能不能决定要不要打开。记下含糊、撞车、无分组、大源只指到仓库根、wiki-ext 目录带敏感词或比原生更难用。
  3. 正确性。对照磁盘：index 与文件是否一一对应；链接是否打得开；入库副本是否被改过；有没有大源整份拷贝；软链接能否解析，不能解析时 index 有没有可重建定位；wiki 是否改了 sources 原文；同一事实是否两页打架且未标明；wiki-ext 是否链到原生层。
  4. 脱敏。对范围内每个 wiki-ext 页：机械扫描（密钥形态、1on1、绩效薪酬、家人住址、/Users/、.env 等，同生成流程）；通读后按禁止表打档；对照原生页看是否投影、结论有没有被改歪、改法有没有用错。原生 wiki 同样扫密钥，命中则两边都删。已对外交付过、或 index 仍列着、却未扫过的页，记为覆盖缺口。
  5. 按协议修。效率问题优先改目录说明和分组。正确性按写入规则改。脱敏按「怎么做信息脱敏」四种改法改 wiki-ext（密钥同时改原生），不要手写一套对不上的对外稿。
  6. 再读一遍三份 index，抽查刚修过的 wiki-ext 页。
  7. 自行 commit。记录：范围、效率问题、正确性问题、脱敏命中（原文摘录 → 类别 → 改法）、改了哪些文件。仓内提交不必等人。要把 wiki-ext 拷给外部，仍走外发确认。

修完算过关：正确性、脱敏表里没有未处理项；抽一个以后会问的问题，只靠 index 能选到唯一合理的下一篇（或明确「仓里没有」）。脱敏未过关不得进入外发；过关也还要等人确认才能拷贝。

生成脱敏 wiki 并交给外部

一次只处理一份列清楚的页面清单（原生 wiki 里哪些页要反映到 wiki-ext）。不要说「把整个仓脱敏一下」却不给路径。

  • 清单来自本次要同步的页：点名的路径，或相对上次已提交 wiki-ext 的 diff。除非明确要全量，否则不要默认整个 wiki/。
  • 若点的是目录，报告里必须展开成文件列表。没展开就失败。
  • 清单里出现 sources/ → 整次失败。不要对原文做脱敏再外发。
  1. 说明本次是更新 wiki-ext 给外部 Agent。没说清就停，问一句。
  2. 列出将生成的每一个原生页路径，排除 sources。
  3. 对每个文件做机械扫描，命中必须写进报告，不能只写「看起来干净」。至少查：password / token / secret / Bearer / BEGIN PRIVATE / AKSK 形态；/Users/、~/.ssh、.env；1on1、绩效、薪酬、晋升、家人、住址、私人手机号。内网域名表写在 maintain 附录（至少 *.bytedance.net、code.byted.org）。误报要写「误报 + 理由」。
  4. 通读每段，按「什么可以给外部看」分类。扫描没扫到但属于敏感个人或密钥的，同样记下来。
  5. 只改 wiki-ext。对每一处禁止内容，按「怎么做信息脱敏」选一种改法（删除 / 改写留结论 / 泛化 / 整页不生成）。做不到、而你又要求必须给出去 → 整次取消。原生页保持原样。
  6. 更新 wiki-ext/index.md，只保留实际写出的页。对外页里的链接只指向其他 wiki-ext 页。未处理项为空即可 commit 进知识仓。
  7. 写报告（可写在会话里或维护记录里）：清单；每条命中的原文摘录、类别、改法、改成了什么。
  8. 只有在要把 wiki-ext 拷给外部 Agent 时，才等人确认「可以外发」。未确认不准拷贝。仓内生成和提交不必等这一步。

可以交给外部的条件：未处理项为空，你已确认，对方实际拿到的文件都在 wiki-ext 里。跳步骤、夹带原生页、改原生、「大部分过了就先给」、只做正确性巡检没跑脱敏轴就当可以外发，都不算过关。

Agent 还禁止：未确认就开始拷贝；把 ~/.ai-space/ 整仓交给外部；报告没有摘录；密钥打码后仍把能复原的半截写进 wiki-ext。

同一段话怎么改

原生 wiki：「需求 N123：和 PM 张三 1on1 里他说加宽表字段；设计在飞书文档；token=abc；我私下觉得这会影响陪家人的时间；原则是宽表不如事件表。」

片段类别改法wiki-ext 里写成
需求 N123；飞书文档链司内密文保留原样
PM 张三工作身份保留「PM 张三」
1on1 里他说加宽表字段敏感个人包着工作结论改写留结论「PM 张三要求加宽表字段」
token=abc密钥删除（原生 wiki 也删）不出现
会影响陪家人的时间敏感个人删除不出现
宽表不如事件表通用保留原样

对外页整段写成：「需求 N123：PM 张三要求加宽表字段；设计在飞书文档；原则是宽表不如事件表。」
